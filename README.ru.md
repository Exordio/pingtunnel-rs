# protofuse

**Русский** | [English](README.md)

> **protofuse** - туннелирование TCP/UDP/SOCKS5 трафика поверх ICMP и
> произвольных IP-протоколов, со слоем обфускации трафика. Async (tokio): низкая
> память, event-driven, батчинг syscalls, настраиваемый размер кадра (`--jumbo`).
> Поддержаны TCP, UDP, SOCKS5 (CONNECT и UDP ASSOCIATE).

### Истоки

protofuse идейно берёт начало от проекта на Go
[esrrhs/pingtunnel](https://github.com/esrrhs/pingtunnel): от него унаследованы
модель «TCP/UDP-over-ICMP» и базовый wire-формат (protobuf `MyMsg`/`Frame`/
`FrameData`). С тех пор проект существенно разошёлся с прародителем - async-ядро
на Rust, батчинг syscalls, транспорт поверх произвольных IP-протоколов и их
ротация, а также слой обфускации трафика (случайный паддинг, обфускация
заголовка, джиттер keep-alive), которого в оригинале нет. Поэтому совместимость
с оригиналом возможна лишь на общем подмножестве protobuf-полей и не
гарантируется.

#### **В основе - та же модель «TCP/UDP-over-ICMP», переписанная на async-Rust с упором на: батчинг syscalls (меньше sys-CPU), отсутствие GC (ровная память), безмьютексный путь TCP-соединения. Цена - отброшены вспомогательные Go-фичи (GeoIP, pprof, пул-параметры). Узкое место - pps (пакеты в секунду), а не ширина канала, поэтому главный рычаг скорости - --jumbo (крупнее кадр -> меньше пакетов -> ниже CPU).**

> ⚠️ **Только для исследований и обучения. Не используйте в противоправных целях.**

```
            ICMP (echo) либо кастомный IP-протокол
   +--------+   с инкапсулированным TCP/UDP     +--------+        +---------------+
   | client | ------------------------------->  | server | ---->  | целевой адрес |
   | (-l)   | <-------------------------------  |        | <----  |  (-t / SOCKS) |
   +--------+                                   +--------+        +---------------+
 локальный TCP/UDP/SOCKS5                  публичный IP        реальный сервис
```

# Отличия ?

## 1. Язык и рантайм

| Характеристика | Go-оригинал | Этот порт (Rust) |
|----------------|-------------|------------------|
| Конкуренция | горутины + GC + планировщик Go | async-задачи на tokio, без GC |
| Память | GC, пилообразный профиль, ~20-1000Mb+, паузы | детерминированная, ~20–150 МБ, без пауз |
| Накладные на соединение | горутина (стек ~KB) + каналы | tokio-task (дешевле горутины) |


## 2. Архитектура ввода-вывода (главное отличие по перфу)
- Батчинг syscalls. Это ключевое. Go-версия делает «один syscall на пакет» (ReadFrom/WriteTo). Здесь — recvmmsg/sendmmsg: десятки ICMP-пакетов за один вызов ядра (icmp.rs). Именно это убирало основную долю sys-CPU на сервере (в комментарии к файлу — ~72%).
- Модель тасков. Один read-таск принимает пачки и демультиплексирует по conn-id, один write-таск собирает исходящее и шлёт пачкой; каждое TCP-соединение — отдельная задача со своим FrameMgr (единоличный владелец, без Mutex вокруг состояния фреймов).
- Модель тиков/времени. Go использует кэшированное «now» (обновляется отдельной горутиной) и грубый тик. В этом порте приведён цикл соединения к адаптивному тику (10мс при работе / 500мс на простое) и кэшированию времени в update() — раньше был busy-poll 1мс.

## 3. Функциональные отличия (фичи)
- ❌ GeoIP-фильтр SOCKS5 (--s5filter/--s5ftfile) не реализован — нужна база MaxMind + mmdb-ридер. Флаги принимаются для совместимости, но не фильтруют.
- ❌ --profile (pprof) — это Go-инструмент, в Rust его нет.
- ❌ --maxprt/--maxprb (параметры серверного пула обработки) не нужны — диспетчеризация прямая, без пула воркеров.
- ✅ TCP-проброс, SOCKS5 CONNECT, чистый UDP, SOCKS5 UDP ASSOCIATE, форвардинг через socks5/http-прокси, шифрование (AES-128/256-GCM, ChaCha20-Poly1305).
- ➕ Сверх оригинала: транспорт поверх произвольного IP-протокола и ротация протоколов, плюс слой обфускации трафика - случайный паддинг, обфускация заголовка, джиттер keep-alive.

## 4. Протокол и совместимость
- Wire-формат сохранён — те же protobuf MyMsg/Frame/FrameData и логика фреймов, поэтому Rust- и Go-стороны в принципе могут общаться (но это не точно).
- ID соединения — 32 hex-символа случайно (в Go — MD5). На протокол не влияет, это просто строковый ключ.

## Как это работает

Каждый пакет транспорта несёт в своём payload сериализованное protobuf-сообщение
`MyMsg` (идентификатор соединения, тип, целевой адрес, данные, ключ и т.д.),
опционально зашифрованное. Поверх ICMP по умолчанию клиент отправляет echo
request (тип 8), а сервер отвечает echo reply (тип 0); тот же payload `MyMsg`
может вместо этого идти поверх произвольного номера IP-протокола (см.
[Транспорт поверх кастомного IP-протокола](#транспорт-поверх-кастомного-ip-протокола)).

Поскольку ICMP — ненадёжный канал без гарантий доставки и порядка, для **TCP**
поверх него реализован собственный надёжный транспорт `FrameMgr`:

- скользящее окно и нумерация фреймов;
- повторная отправка по таймауту и по запросу получателя (REQ);
- кумулятивные подтверждения (ACK);
- ping/pong для оценки RTT и heartbeat для контроля живости;
- опциональное сжатие фреймов (zlib).

Для **UDP** надёжный слой по умолчанию выключен — датаграммы передаются как есть
(ненадёжно, как и сам UDP). Флаг `--udp_rel 1` (на клиенте) пускает датаграммы
через **тот же** `FrameMgr`, что и TCP: добавляются ретрансмиссия и порядок, а
границы датаграмм сохраняются через префикс длины. Полезно, когда ICMP-канал
теряет много пакетов. Работает и для чистого UDP-проброса (`-t`), и для **SOCKS5
UDP ASSOCIATE** (`--sock5 1`). Флаг нужен только клиенту — сервер распознаёт
надёжное UDP-соединение по connect-пакету.

## Сборка

Требуется Rust (edition 2024, минимум 1.85) и `protoc` (Protocol Buffers compiler), который
вызывается на этапе сборки для генерации Rust-кода из `.proto`.

```bash
# Установка protoc (примеры)
#   Arch:   sudo pacman -S protobuf
#   Debian: sudo apt install protobuf-compiler

cargo build --release
# бинарь: target/release/protofuse
```

## Права доступа (важно)

Для приёма/отправки ICMP сервер открывает **RAW-сокет**, что требует прав
`root` или capability `CAP_NET_RAW`:

```bash
# вариант 1 — запуск под root
sudo ./target/release/protofuse --type server --key 123456

# вариант 2 — выдать capability бинарю (тогда без sudo)
sudo setcap cap_net_raw+ep ./target/release/protofuse
./target/release/protofuse --type server --key 123456
```

**Клиент** дополнительно умеет работать без привилегий: если RAW-сокет
недоступен, он автоматически откатывается на непривилегированный
ICMP datagram-сокет (если `net.ipv4.ping_group_range` это разрешает — на
большинстве дистрибутивов разрешено по умолчанию). Это аналог android-режима
оригинала. Серверу datagram-режим не подходит — ему нужен RAW.

(Опционально) отключить системные ответы ядра на ping, чтобы они не мешали:

```bash
echo 1 | sudo tee /proc/sys/net/ipv4/icmp_echo_ignore_all
```

## Использование

### Сервер

```bash
sudo ./protofuse --type server --key 123456
```

### Клиент: SOCKS5

Поднимает локальный SOCKS5-прокси, весь трафик которого идёт через ICMP-туннель
до сервера (TCP включается неявно):

```bash
./protofuse --type client -l :1080 -s СЕРВЕР --sock5 1 --key 123456
```

С аутентификацией:

```bash
./protofuse --type client -l :1080 -s СЕРВЕР --sock5 1 \
             --s5user user --s5pass pass --key 123456
```

### Клиент: проброс TCP

Весь трафик на локальный порт `4455` пробрасывается на `СЕРВЕР:4455`:

```bash
./protofuse --type client -l :4455 -s СЕРВЕР -t СЕРВЕР:4455 --tcp 1 --key 123456
```

### Клиент: проброс UDP

```bash
./protofuse --type client -l :4455 -s СЕРВЕР -t СЕРВЕР:4455 --key 123456
```

> Здесь `СЕРВЕР` — публичный IP или домен машины с запущенным сервером,
> а `-t` — конечный адрес, куда сервер пробросит трафик.

Надёжный UDP (ретрансмиссия + порядок поверх теряющего ICMP-канала):

```bash
./protofuse --type client -l :4455 -s СЕРВЕР -t СЕРВЕР:4455 --udp_rel 1 --key 123456
```

## Шифрование

Payload ICMP можно шифровать AEAD-шифром. Поддерживаются `aes128`, `aes256`,
`chacha20`. Ключ задаётся как base64 нужной длины **или** как парольная фраза
(тогда ключ выводится через PBKDF2-HMAC-SHA256). Режим и ключ должны совпадать
на клиенте и сервере:

```bash
# сервер
sudo ./protofuse --type server --key 123456 \
     --encrypt chacha20 --encrypt-key "моя-секретная-фраза"

# клиент
./protofuse --type client -l :1080 -s СЕРВЕР --sock5 1 --key 123456 \
     --encrypt chacha20 --encrypt-key "моя-секретная-фраза"
```

## Форвардинг через прокси

Сервер может пробрасывать исходящие соединения не напрямую, а через внешний
прокси (`socks5` или `http` CONNECT):

```bash
sudo ./protofuse --type server --key 123456 --forward socks5://localhost:2080
sudo ./protofuse --type server --key 123456 --forward http://localhost:8080
```

UDP-форвардинг через прокси поддерживается только для `socks5` (UDP ASSOCIATE).

## Транспорт поверх кастомного IP-протокола

По умолчанию транспорт работает поверх ICMP (IP-протокол 1). Флаг `--ip_proto N`
гонит тот же wire-формат поверх другого номера IP-протокола - например `253`
или `254`, зарезервированных IANA под эксперименты (RFC 3692). Это штатный,
регулярно используемый режим (не экспериментальный), хотя и с перечисленными ниже
ограничениями. **Там, где это позволяет сеть на пути, его следует использовать
не церемонясь** - это самый эффективный рычаг против ограничений, нацеленных на
ICMP. Формат пакета в остальном не изменяется (те же 8 байт псевдо-echo заголовка
и protobuf); изменяется только поле `protocol` в IP-заголовке, формируемое ядром.

Назначение: во многих сетях пропускная способность ICMP ограничивается на уровне
класса трафика (шейпер или классификатор, нацеленный именно на ICMP). Перенос транспорта на
другой IP-протокол полностью обходит это ICMP-специфичное ограничение. При
измерении достигнута скорость порядка 150-160 Мбит/с с `--jumbo 1400` на канале,
где пропускная способность ICMP была сильно ограничена.

Ограничения (по которым он и не является режимом по умолчанию):
- Номер протокола должен совпадать на клиенте и сервере.
- Требуется RAW-сокет на обоих концах (root или `CAP_NET_RAW`); непривилегированный
  datagram-режим недоступен (в отличие от ICMP).
- Режим несовместим с NAT: трансляция выполняется только для TCP, UDP и ICMP,
  поэтому у кастомного протокола отсутствует обратный путь через stateful-NAT.
  Работа возможна только при прямой маршрутизации либо через оборудование,
  пропускающее неизвестные протоколы без изменений.
- Протокол легко блокируется: в отличие от ICMP отсутствует сопутствующий
  легитимный трафик, поэтому он может быть отброшен целиком при обнаружении.
- Маскировка под ICMP-эхо отсутствует. Само содержимое пакета, впрочем, можно
  свести к чистому шуму [обфускацией заголовка](#обфускация-трафика)
  (`--obfs`), убирающей статический псевдо-echo заголовок на кастомных протоколах.

```bash
# сервер
sudo ./protofuse --type server --key 123456 --ip_proto 253

# клиент
./protofuse --type client -l :1080 -s СЕРВЕР --sock5 1 --key 123456 --ip_proto 253
```

Проверка прохождения протокола по сети (выполняется на сервере во время передачи):

```bash
tcpdump -ni any 'ip proto 253'
```

Для возврата к стандартному ICMP флаг не указывается (либо указывается значение `1`).

### Ротация протокола (`--ip_proto_range`)

Вместо одного фиксированного протокола флаг `--ip_proto_range LO-HI` (напр.
`100-254`, в пределах `1..=254`) распределяет трафик по диапазону номеров
IP-протоколов: клиент выбирает случайный протокол на каждое соединение. Это
нацелено на пер-флоу классификаторы - каждый протокол несёт лишь короткоживущую
часть трафика.

Поскольку RAW-сокет принимает ровно один номер протокола, приём в этом режиме
идёт через один `AF_PACKET`-сокет с BPF-фильтром в ядре, пропускающим только
входящие пакеты с номером IP-протокола в пределах диапазона; сервер отвечает на
том же протоколе, на котором пришёл запрос. Отправка использует RAW-сокеты,
открываемые лениво под используемые протоколы, поэтому ядро по-прежнему строит
IP-заголовок и фрагментирует jumbo-кадры.

Диапазон должен совпадать на клиенте и сервере; на обоих концах нужен root /
`CAP_NET_RAW`. Действуют все ограничения кастомного протокола выше (нет прохода
через NAT, легко блокируется, нет маскировки под ICMP); вдобавок хост, шлющий
трафик по множеству IP-протоколов, сам по себе - заметная аномалия для
классификаторов трафика: ротация помогает против пер-флоу шейпинга, но не против
обнаружения.

```bash
# сервер
sudo ./protofuse --type server --key 123456 --ip_proto_range 100-254

# клиент
./protofuse --type client -l :1080 -s СЕРВЕР --sock5 1 --key 123456 --ip_proto_range 100-254
```

Проверка прохождения ротируемых протоколов (выполняется на сервере во время передачи):

```bash
tcpdump -ni any 'ip[9] >= 100 and ip[9] <= 254'
```

`--ip_proto_range` перекрывает `--ip_proto`.

## Обфускация трафика

Туннель можно вычислить не только по номеру IP-протокола, но и по статистическим
признакам: постоянному размеру пакетов, статичным первым байтам и идеально
периодическому «пульсу» keep-alive. protofuse предлагает три независимые меры,
убирающие эти признаки; каждая по умолчанию выключена и включается своим флагом.

### Случайный паддинг (`--pad N`)

Постоянный размер пакета - сильная сигнатура туннеля: если каждый кадр, скажем,
ровно 1400 байт, этот паттерн бросается в глаза. С `--pad N` к каждому пакету
перед шифрованием дописывается случайное число «мусорных» байт (`0..=N`), так что
размер на проводе меняется от пакета к пакету (например, 1312, 1345, 1302 байта),
что ломает статистический анализ по длинам.

Паддинг лежит внутри шифруемой области (отдельное protobuf-поле) и игнорируется
получателем, поэтому согласовывать значение между концами не нужно - каждая
сторона может задать своё. Разумные значения - `64..256`. `0` (по умолчанию)
выключает паддинг.

```bash
./protofuse --type client -l :1080 -s СЕРВЕР --sock5 1 --key 123456 \
            --encrypt chacha20 --encrypt-key SECRET --pad 256
```

### Обфускация заголовка (`--obfs`)

Без обфускации внутренний заголовок (id сессии и флаги ping/pong/data) идёт перед
зашифрованными данными, поэтому первые байты каждого пакета статичны - идеальная
сигнатура для файрвола. С `--obfs` весь внутренний заголовок склеивается с данными
и шифруется целиком (AEAD), а статическая псевдо-echo обёртка снимается; на проводе
остаётся лишь 12-байтный случайный nonce и шифртекст. Пакет превращается в сплошной
псевдослучайный шум от первого байта до последнего, без единого постоянного поля,
за которое можно зацепиться.

Поскольку снятие echo-обёртки даёт пакет, который уже не является валидным ICMP,
`--obfs` требует кастомного IP-протокола (`--ip_proto` / `--ip_proto_range`) и
шифрования (`--encrypt`). Флаг должен совпадать на клиенте и сервере.

```bash
# сервер
sudo ./protofuse --type server --key 123456 --ip_proto 253 \
     --encrypt chacha20 --encrypt-key SECRET --obfs

# клиент
./protofuse --type client -l :1080 -s СЕРВЕР --sock5 1 --key 123456 --ip_proto 253 \
     --encrypt chacha20 --encrypt-key SECRET --obfs
```

### Джиттер keep-alive (`--keepalive`, `--keepalive_jitter`)

Чтобы домашние роутеры и NAT-таблицы провайдера не закрывали сессию на кастомном
IP-протоколе, туннель шлёт фоновые keep-alive пакеты. Если слать их строго через
фиксированный интервал, образуется идеальный периодический пульс, по которому
автоматический скрипт вычисляется мгновенно. `--keepalive N` задаёт базовый
интервал (сек); `--keepalive_jitter J` добавляет случайный шум `+/- J` секунд
вокруг него (пересчитывается на каждый интервал через `sleep`, а не фиксированный
`interval`), так что паузы между фоновыми пакетами всегда разные и выглядят как
хаотичная активность живого пользователя.

```bash
# база 20с, фактический интервал равномерно в 15..25с
./protofuse --type client -l :1080 -s СЕРВЕР --sock5 1 --key 123456 \
            --keepalive 20 --keepalive_jitter 5
```

По умолчанию `--keepalive` равен `1` секунде с нулевым джиттером, что сохраняет
прежнее поведение. Флаг влияет на транспортный keep-alive клиента; пер-соединенческие
ping живости он не затрагивает.

## Производительность и тюнинг

Узкое место ICMP-туннеля — **не ширина канала, а packets-per-second (pps)**:
каждый кадр едет отдельным ICMP-пакетом, и потолок упирается в то, сколько
пакетов в секунду успевает обработать ядро/CPU. На практике один TCP-поток
уверенно даёт **~50 Мбит/с (~6 МБ/с)** даже дефолтным кадром 888 Б (замер через
WAN ~44 мс RTT до 1-vCPU сервера) — и заметно больше при меньшем RTT, свободном
CPU, поднятых буферах, `--jumbo` или нескольких потоках.

Чтобы выжать максимум, на **сервере и клиенте** (Linux) полезно поднять буферы
и снять встроенные лимиты ICMP. Создайте `/etc/sysctl.d/99-protofuse.conf`:

```ini
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.core.rmem_default = 262144
net.core.wmem_default = 262144
# очередь входящих пакетов — чтобы ОС не дропала ICMP при наплыве
net.core.netdev_max_backlog = 10000
# снять лимит на частоту ICMP
net.ipv4.icmp_ratelimit = 0
net.ipv4.icmp_ratemask = 0
```

Применить: `sudo sysctl -p /etc/sysctl.d/99-protofuse.conf`.

> Без поднятия `rmem_max/wmem_max` ядро по умолчанию режет буфер сокета до
> ~200 КБ, что мешает держать окно при заметном RTT.

**Главный «хак» под скорость — крупнее кадр** (`--jumbo N`): меньше пакетов на
байт → меньше pps → ниже CPU и выше потолок. По умолчанию кадр 888 Б (маскировка
под обычный ping). Ориентиры на один поток (зависят от RTT/CPU/линка — **реально
может быть больше**):

| `--jumbo` | один поток | примечание |
|-----------|-----------|------------|
| 0 (888 Б) | **~50 Мбит/с (~6 МБ/с)** | дефолт, маскировка под ping; замер через WAN ~44 мс RTT |
| 1400      | выше | ровно под MTU, без фрагментации |
| 8000      | ещё выше | лучший single-stream; >MTU → IP-фрагментация. (возможны потери) |

## Архитектура реализации

| Файл                 | Назначение                                                            |
|----------------------|-----------------------------------------------------------------------|
| `src/main.rs`        | разбор аргументов (clap), запуск клиента или сервера                  |
| `src/proto.rs`       | сгенерированные protobuf-типы (`MyMsg`, `Frame`, `FrameData`) и константы |
| `src/icmp.rs`        | ICMP/кастомный-протокол сокет, сборка/разбор echo, кодек `Wire` (упаковка `MyMsg`, шифрование, паддинг, обфускация заголовка) |
| `src/framemgr.rs`    | надёжный транспорт поверх ICMP (скользящее окно, ACK/REQ, ping/pong, heartbeat, сжатие) |
| `src/ring.rs`        | кольцевые буферы: байтовый (`RBuffer`) и по id фреймов (`ROBuffer`)   |
| `src/crypto.rs`      | AES-128/256-GCM, ChaCha20-Poly1305, вывод ключа (base64/PBKDF2)       |
| `src/icmp.rs`        | async ICMP-сокет (`AsyncFd`), батчинг `recvmmsg`/`sendmmsg`, сборка echo, `MyMsg` |
| `src/socks5.rs`      | SOCKS5: async-рукопожатие, разбор запросов, кодирование адресов, UDP-датаграммы |
| `src/forward.rs`     | async-форвардинг через socks5/http-прокси                            |
| `src/client.rs`      | клиент: приём локальных TCP/UDP/SOCKS5, туннелирование в ICMP         |
| `src/server.rs`      | сервер: приём ICMP, подключение к целям (TCP/UDP, напрямую или через прокси) |
| `src/util.rs`        | время, генерация id соединений, резолвинг адресов, счётчики           |

**Модель — async на tokio** (worker-пул = числу ядер). Каждое соединение — это
задача (а не ОС-поток), работает по событиям (входящий фрейм / локальные данные /
таймер), без busy-poll. Один read-таск принимает ICMP пачками (`recvmmsg`) и
демультиплексирует по conn-id; один write-таск собирает исходящее и шлёт пачкой
(`sendmmsg`). Для **TCP** каждое соединение держит `FrameMgr` (надёжная доставка,
единоличный владелец без `Mutex`); для **UDP** — прямой проброс датаграмм без
надёжного слоя (как и в оригинале) либо через `FrameMgr` при `--udp_rel 1`
(чистый UDP и SOCKS5 UDP ASSOCIATE). Память ~20–150 МБ (зависит от числа соединений).

Поддержаны: **TCP-проброс**, **SOCKS5 CONNECT** (TCP), **чистый UDP-проброс**
(`-l :порт -t host:порт` без `--tcp`/`--sock5`) и **SOCKS5 UDP ASSOCIATE**.

## Тесты

```bash
cargo test
```

Покрытие (23 теста, не требуют привилегий):

- **`framemgr`** — петлевой обмен двух `FrameMgr`: рукопожатие, многокадровый
  поток в обе стороны, **восстановление после потери ~1/3 фреймов**, сжатие;
- **`icmp`** — контрольная сумма, раскладка echo-заголовка, round-trip `MyMsg`,
  **случайный паддинг** (рандомизация размера + целостность полезной нагрузки) и
  round-trip **обфускации заголовка**;
- **`crypto`** — round-trip для всех трёх режимов, отказ при неверном ключе;
- **`ring`** — кольцевые буферы (перенос через край, переполнение, окно id);
- **`socks5`** — кодирование/разбор адресов и UDP-датаграмм.

Полный сквозной тест туннеля требует прав на RAW-сокеты для сервера:

```bash
sudo ./scripts/e2e_test.sh        # или после setcap — без sudo
```
